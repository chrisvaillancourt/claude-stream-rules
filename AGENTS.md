# stream-rules

A Claude Code mod (function-hook plugin). `README.md` is the user-facing spec; keep it in step with any behavior change in the same commit.

## Layout

- `hooks/rules.ts`: pure rule-file handling. Frontmatter parsing (a small YAML subset), validation, regex compilation (leading `(?i)`/`(?m)`/`(?s)` become JS flags), scope parsing, globs, and matching a text or a tool call against the loaded rules. No `$`, no I/O.
- `hooks/policy.ts`: pure decisions and text. Options, command parsing, repeat eligibility, the correction cap, the text the model is given, judge prompt and verdict parsing, the draft prompt and draft extraction. No `$`, no I/O.
- `hooks/lifecycle.ts`: who owns follow-up work, as one pure state machine: `transition(session, event, config) → { state, actions }`, `classifyIngress`, `isCurrent`, claims and their release. Unit-tested as a table in `lifecycle.test.ts`.
- `hooks/register.ts`: wiring. Rule loading (`$.fs`), the `turn.step` watcher, the `tool.call` guard, corrective turns, judged rules, both commands, `$.state`. Keep logic thin here; test behavior through the engine in `register.test.ts`.
- `types/index.d.ts`: the mod's types and its `$.state` contract (`PluginState['stream-rules']`). Every `$.state` key the module uses must be declared here.
- `examples/*.md`: example rules, one per scope. Never loaded unless the person copies them into a rules folder.
- `.claude-plugin/plugin.json`: manifest and `userConfig` options. `marketplace.json` makes the repo its own marketplace.
- `scripts/check.sh`: the commit gate (validate, test, typecheck).
- `.claude-plugin/types/` and `tsconfig.json` are generated by Claude Code when it loads the mod from a watched folder. They're gitignored; don't commit or hand-edit them.

## How it works (design invariants for this mod)

- **Rules live outside the prompt.** Rule files are read from `~/.claude/stream-rules/*.md` and `<cwd>/.claude/stream-rules/*.md` (project wins by name). They are never put in the system prompt or the tool list, so loading them costs no tokens and doesn't touch the prompt cache. Not `.claude/rules/`, which Claude Code loads as instructions itself.
- **Three enforcement paths, chosen by where the match happens:**
  1. *Tool calls* (`tool.call`, main loop and subagents): an interrupting rule answers `{ deny: message }` before `next`, so the tool never runs; the denial carries every matched rule's message, non-interrupting ones too, because a rule counts as fired only once its message was delivered. A non-interrupting rule alone runs the tool and adds the message as `context`; when the call is refused beneath (`next` answers `{ deny }`), the message is appended to that denial instead. The guard's `.catch` **fails open** (the call runs) and records the error for `/stream-rules status`: rules are guidance, not a security boundary, and a broken rule must not block every tool.
  2. *Streamed text or thinking on the main loop* (`turn.step`): text is matched per content block as it streams, so a match spanning chunks is found. On an interrupting match the hook stops yielding (the matching chunk and everything after it, tool calls included, never reach the engine), stores a pending correction in `$.state` **before** calling `$.turn.abort`, then drains the stream. The corrective prompt is submitted from a `$.clock.after(0)` timer after that turn's `turn.complete`, guarded by the pending record's `turnId`. Text yielded before the match stays shown and recorded: there is no rollback (checked live on 2.1.310).
  3. *Streamed text in a subagent*, and non-interrupting prose rules anywhere: `$.session.append` a user-role reminder into that loop (`agentId` for a subagent). `$.turn.abort` can't stop a subagent.
- **Judged rules** (a `question`) never fire mid-stream. After a main-loop turn ends with `reason: 'answer'`, a timer asks the judge model one yes/no question per eligible rule (its `condition`, if any, prefilters the answer), capped by `judgeMaxPerTurn`. A yes delivers a reminder (or a corrective turn with `judgeAction: correct`). A failed or unclear verdict commits nothing.
- **Bounded corrections.** `maxCorrections` caps corrective turns per prompt (reset by a superseding ingress). Each rule has a repeat policy, counted in model responses per loop (`turn.step` calls), not whole turns: `once` (default for text and thinking), `always` (default for tools), `after-gap` (`gap` responses since it last fired). A rule's firing is claimed with `update` before it acts.
- **Ownership is one state machine (`hooks/lifecycle.ts`).** Every event that can change who owns a correction or a judgment (ingress by origin, `turn.start`, a stream match, the abort's result, `turn.complete`, the correction timer, a judge result, a tool match, a release, on/off, `/clear`, reload) goes through `transition` inside one `update` of the session atom, and the pending correction lives in that same atom. `transition` returns actions; register.ts performs them and never decides ownership itself.
  - *Epoch.* A superseding ingress, `/stream-rules on|off` and `/clear` start a new epoch and drop the pending correction (releasing its claim). A main turn records the epoch it started under; only a turn of the current epoch is stopped or judged.
  - *Ingress table* (`classifyIngress`, on `prompt.submit`): **supersede** for `composer`, `sdk`, `bridge`, `channel`, `slack-ping`, `coordinator`, `projects-relay`, `auto-continuation`, `scheduled-trigger` (scheduled tasks and `/loop`), any other plugin's submission, `unclassified` unless meta, any origin not listed, and every slash command except this mod's own; **preserve** for `task-notification`, `peer`, `peer-send-message`, `observer`, `observer-activity`, meta `unclassified` (idle notices, receipts) and this mod's own corrective prompt; **ignore** `/stream-rules` and `/stream-rules-draft` (on/off is its own event). Unknown origins supersede because dropping a stale correction is the safe direction.
  - *Check before every visible action.* After the claim's `await`, and right before `$.turn.abort`, `$.prompt.submit`, `$.session.append` and a tool denial, register.ts confirms the owner is still current through `confirm` (a versioned `update` of the same value, not a plain `read`: in the test kit a read returned this module's own earlier write after another hook's later write had landed). A failed check releases the claim, so the rule isn't spent unseen. A tool denial checks only that the mod is on: it acts on the call in hand, which no newer prompt makes stale.
  - *Claims.* A claim records each rule's previous firing mark; `release` restores marks that still hold the claimed value. Undelivered work (a refused append or submit, a lost owner) is released.
- **Stale work is dropped, not resurrected.** A pending correction left by a hot reload (timers die) is discarded and logged at the next `session.start`. `/clear` (`session.end` with `reason: 'clear'`) resets repeat state, pending work and the draft.
- **Drafts never write themselves.** `/stream-rules-draft <complaint>` asks the draft model for a rule, validates it with the live parser, counts what it would have matched in recent history through the live matchers (`draftCheck`: replies for text scope, `SessionMessage.toolUses` for tool scope), and holds it in `$.state`. Only `/stream-rules-draft save [project|user]` writes it, refusing to overwrite an existing file unless `overwrite` is given.
- **Injected text** speaks of the reply and the work, never of the model's thinking or reasoning, even for a rule scoped to `thinking`.

## Checked live (Claude Code 2.1.310, `claude -p`, Haiku)

- `$.turn.abort({ turnId })` called (not awaited) from inside this turn's `turn.step` hook resolves; the stream beneath ends, `turn.complete` comes with `reason: 'aborted'`, and its `answer` is only what was yielded before the match. A `$.prompt.submit` from a `$.clock.after(0)` timer after that starts the corrective turn, headless too.
- A `tool.call` deny stops a Bash call before it runs; the model reports the refusal.
- The mod's own corrective prompt reaches `prompt.submit` with `origin: { kind: 'plugin', name: 'stream-rules' }`, so it doesn't start a new epoch; a `-p` prompt arrives as `{ kind: 'sdk' }` and does.
- A judged rule's `$.model.complete` runs after the answer in `-p`, but the reminder append is then refused ("this session keeps no conversation to append to"): the run is over. The error is recorded, not silent.
- `$.session.append({ agentId })` into a running subagent is stored, but a subagent that writes its text and hands back in the same response never reads it.

## Commands

```sh
scripts/check.sh            # claude plugin validate . && claude plugin test . && typecheck
scripts/check.sh --no-tsc   # when TypeScript isn't available
```

All gates must pass before every commit. A behavior change needs a test in `hooks/*.test.ts` (the `claude-code/testing` kit: `mock.clock`, `mock.store`, `mock.env`, and `on(...)` hooks that stand for the engine beneath the plugin) written first and seen failing for the intended reason, then the change that makes it pass.

To try the mod in a live session: `claude --plugin-dir .` (interactive sessions hot-reload on save), or `claude -p --plugin-dir . "<prompt>"` for a headless run (always loads fresh; hooks that need a terminal won't fire). `claude --debug` logs every skipped hook and refused result.

## Design invariants (apply to every mod built from this template)

- **Main conversation vs subagents.** Events from a subagent's loop carry `e.agentId` (`agent_id` on `classic.*` events). Decide explicitly whether the mod acts on subagents; by default return `next(e)` early for them.
- **Hot reloads reset module variables** (timers included). `register` and `session.start` run again; `$.state` and `$.store` survive. Anything that must persist goes in state or store. Change an atom's `shape` tag when its stored type changes.
- **Never throw out of a hook or timer for reporting.** Logging, status and toasts are best effort. A hook that guards (denies a tool call, drops a prompt) gets a `.catch` that decides fail-open or fail-closed deliberately (`next.called ? next(e) : { deny }`).
- **Headless sessions** (`e.isInteractive === false`, `claude -p`) have no terminal: no panes, `$.ui.notify` fails, `$.session.compact` rejects. Skip or degrade explicitly.
- **Cost and the prompt cache.** Anything that calls a model (`$.model.complete`, `classify`, `fork`, `$.agent.spawn`) is billed to the person. Say what it costs in the README, bound it with options, and don't change the system prompt or tool list per turn (that rewrites the whole prompt cache).

### Engine constraints found the hard way (Claude Code 2.1.29x–2.1.310)

- `$.prompt.submit` is refused from inside a `command.run` hook (it would wait on the turn the hook holds). Submit from a `$.clock.after(0, …)` timer.
- `$.session.compact` rejects while a turn runs and in headless sessions.
- A plugin's submitted prompt never expands `@` mentions; `$.prompt.fill` lets the person send it instead.
- `$.model.fork` replays the main thread's last request, which ends before the turn's final answer: quote the answer into the fork prompt if the fork needs it.
- The engine already prefixes `$.ui.status`, `$.ui.toast` and command output with the plugin name; don't add `stream-rules:` there. `$.ui.log` lines keep the prefix.
- A model `Write` outside the project raises a permission prompt; have the plugin write its own files with `$.fs.write` (it creates directories). `$.fs.write` replaces the whole file; there is no append.
- `turn.step` hooks are async generators in the path of every request: always pass the stream through (`yield* next({ ...e, effort })`). A rewritten `model` must be a full id (`claude-haiku-5-5`); an alias failed with `unrecognized_model`. Changing `effort` per request keeps the prompt cache (Opus, Sonnet, Haiku 5.5); changing `model` rereads everything uncached. The UI keeps showing the session's model and effort, so surface a rewrite with `$.ui.status`.
- `tool.call`: `const r = await next(e); return { ...r, context: [text] }` adds text the model reads after the tool result and the person never sees; `{ deny: reason }` blocks the call. A `tool.call` hook without `.catch` is reported by validate as a gate: give it one that fails open or closed on purpose.
- Haiku 5.5 rejects `temperature`/`top_p`/`top_k`, `budget_tokens` and assistant prefill with a 400. Prices step up 5x above 100K prompt tokens.
- Side calls (forks, completions, subagents, compaction) use the "everything else" prompt-cache bucket (5m on a subscription), not the main conversation's 1h one. Cache reads still count against plan usage.
- Text a hook injects for the model must not talk about the model's thinking or reasoning ("you can't see it", "doesn't count"): Opus 5.5's reasoning-extraction safeguard refused such a request. Phrase it in terms of the reply and the work.
- Don't build on instructions the model can ignore: a gate that "asks" the model to do something first failed live. Enforce in a hook, or give the model the information and let it decide.
- `/clear` is `session.end` with `reason: 'clear'` and no `session.start` after it: reset per-conversation state there.

### Bugs that recur in these mods (check every change against them)

Reviews of relay, defer-queue and prewalk kept finding the same family: a boolean flag left stale by a late event (track the running `turnId` instead), a message lost on a path nobody tested (a refused submit, a release racing a new hold), a timer or async step acting for a run that was cancelled or replaced (guard with a `runId` and re-check after every `await`), state that survived `/clear` or a reload when it shouldn't (or didn't when it should), and engine state copied into the mod's own flags (decide from facts at decision time). Two review rounds of blockers in the same mechanism means change the mechanism.

### Test kit notes

- A hook that answers an op on `$` (`command.register`, `fs.read`, `model.complete`, `ui.toast`, `session.messages`) returns `{ value }` or `{ deny }`; a hook that answers an event (`session.start`, `turn.start`, `turn.complete`) returns the event's result directly.
- One bottom hook per event per test file (a second registration errors). Test files with JSX are `.test.tsx`.
- Use `mock.clock(on)` and `clock.advance`/`settle` for time; there is no `setTimeout`.
- A throwing mock hook is skipped rather than surfacing its error, so test decisions that depend on an error's text as pure functions in `policy.ts`.
- Any helper that receives `$` must be a top-level function: the engine's static check refuses a module that passes `$` to a closure defined inside `register`. `atom({ plugin, key })` takes string literals, not a const.
- The kit accepted a wrong tool-input shape at runtime that `tsc` caught: run the typecheck.

### Live checks

The test kit stands in for the engine; it can't show what the engine really does. Before building on an engine behavior the types don't state, probe it: a throwaway observer mod (`--plugin-dir`) that logs events with `$.fs.write`, and one short live session, with `--model haiku` to keep it cheap. Record the Claude Code version a behavior was checked on. Headless runs (`claude -p`) create transcript folders under `~/.claude/projects/`; run them from a scratch directory.

## Conventions

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`).
- Bump `version` in `plugin.json` for every release users should get. Installs from GitHub run a copy, and `claude plugin update` only replaces it when the version changes. An install whose marketplace is a local clone runs from the clone itself: edit, then `/reload-plugins`.
- MIT licensed: `LICENSE` at the root, and `plugin.json` says `MIT`. Treat the repo as public: no secrets, tokens, session IDs, personal paths or employer-specific details in code, tests, docs or commit messages.
- Don't add Claude or AI attribution trailers to commits.
